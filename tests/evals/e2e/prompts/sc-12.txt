The dbservice codebase has a concurrent update problem: callers do read-modify-write on order records by hand, so two concurrent writers silently lose updates (the classic lost-update anomaly). Fix it with optimistic concurrency control. Create a NEW module src/order_store.py exposing exactly this public API. (1) class ConflictError(Exception): raised whenever a conditional write observes a stale version; instances must carry the attributes order_id, expected_version and actual_version. (2) class OrderStore: an in-memory store of orders keyed by integer order_id, each record holding (status: str, total_cents: int, version: int). Methods: OrderStore() -> empty store. create(order_id: int, status: str, total_cents: int) -> int: insert a new record at version 1 and return 1; raise ValueError if order_id already exists. read(order_id: int) -> tuple: return the snapshot (status, total_cents, version) in that order; raise KeyError for an unknown order_id. write(order_id: int, status: str, total_cents: int, expected_version: int) -> int: CONDITIONAL write - if the record's current version equals expected_version, apply both fields, increment the version by exactly 1 and return the new version; otherwise raise ConflictError (attributes set as above) and leave the record completely unchanged; raise KeyError for an unknown order_id. Versions therefore start at 1 on create and go up by exactly 1 per successful write. adjust_total(order_id: int, delta_cents: int, max_attempts: int = 5) -> int: read-modify-write that adds delta_cents to total_cents, keeps the current status, and returns the new total_cents. It MUST be an optimistic retry loop with this exact attempt protocol: (a) take exactly one snapshot via read; (b) if the public instance attribute interleave_hook is not None, call it exactly once with no arguments; (c) attempt write(...) using the snapshot's version, with NO additional read between the hook call and the write. If the write raises ConflictError, start a fresh attempt; after max_attempts conflicting attempts re-raise ConflictError, in which case delta_cents must not have been applied at all (the store reflects only the rival writes). interleave_hook: a public instance attribute, default None; tests assign a zero-argument callable to it to force interleavings deterministically. ONLY adjust_total ever invokes it (once per attempt, at the point defined above); create/read/write never do. The hook must be invoked with no internal locks held, and the store's public API must be safely callable from inside the hook (the grader's hook performs rival read/write calls on the same store instance). INVARIANT: for any sequence of create/write/adjust_total calls, every update is either applied exactly once or surfaced as a ConflictError - a silently lost update must be impossible. Concretely, if a rival write commits between adjust_total's snapshot and its conditional write, the final total_cents must include BOTH the rival's change and delta_cents (via retry), or a ConflictError must escape after max_attempts; and after any run, version == 1 + (number of successful writes to that order). Also ship the matching schema change for the real database: add a NEW migration file migrations/0002_*.sql (e.g. migrations/0002_add_order_version.sql) that adds an integer version column NOT NULL DEFAULT 1 to the orders table. Do NOT modify migrations/0001_create_orders.sql, and do not change or remove the existing query builders in src/store.py - their current behaviour must keep working.
