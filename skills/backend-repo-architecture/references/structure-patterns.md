# Structure Patterns

Full directory tree skeletons and file responsibilities for the canonical backend archetype.

## Standard service layout

```
backend/
├── entrypoint.py              # No application logic; MODE dispatcher only (OPTIONAL: omit for server-only deployments)
├── alembic/                   # Database migrations (autogenerated from Base metadata)
│   ├── env.py
│   └── versions/
├── alembic.ini
├── pyproject.toml             # Dependencies (fastapi, sqlalchemy, redis, orjson, etc.)
├── Dockerfile
├── .env.example
├── app/                       # Core application package
│   ├── __init__.py
│   ├── application.py         # get_app() factory: constructs FastAPI, adds CORS, includes api_router
│   ├── router.py              # api_router aggregation: includes all domain routers, health checks
│   ├── routing.py             # CustomRequestRoute: request/response logging, timing, exception envelope
│   ├── connection.py          # ConnectionManager (singleton), ConnectionHandler (per-request), get_connection_handler
│   ├── dao.py                 # BaseDao: CRUD, pagination, soft-delete, bulk ops
│   ├── database.py            # Base (DeclarativeBase or declarative_base)
│   ├── lifetime.py            # lifespan: startup (init ConnectionManager, Kafka, Temporal, Redis), shutdown (close all)
│   ├── main.py                # uvicorn runner: uvicorn.run("app.application:get_app", factory=True)
│   ├── telemetry.py           # OpenTelemetry init, instrument_app/db/redis
│   └── utils.py               # ResponseData envelope, helpers
├── config/
│   ├── __init__.py
│   ├── settings.py            # Settings(BaseSettings), module-level `settings = Settings()`
│   ├── logging.py             # setup_logging: structlog/standard logging config
│   └── sentry.py              # configure_sentry (optional)
├── services/                  # Config-driven infra packages (no business logic)
│   ├── kafka/
│   │   ├── producer.py
│   │   └── consumer/
│   │       └── consumer.py
│   └── temporal/
│       ├── client.py
│       └── run.py
├── <domain_pkg>/              # Domain modules (see layouts below)
│   └── ...
└── tests/
    ├── __init__.py
    ├── conftest.py
    └── test_*.py
```

### File responsibilities

| File | Responsibility |
|------|----------------|
| `entrypoint.py` | Dispatches on MODE env (server/consumer/temporal_worker/cron/webhook_server). Server mode runs uvicorn; worker/consumer modes run asyncio.run(service_main()). No business logic. **OPTIONAL**: omit for server-only deployments (Dockerfile CMD can run gunicorn/uvicorn directly). |
| `app/application.py` | `get_app() -> FastAPI`: constructs app instance, sets debug/lifespan/default_response_class, adds CORS middleware, includes api_router, optionally mounts /metrics ASGI app. |
| `app/router.py` | `api_router = APIRouter()`: aggregates domain routers, registers health checks (/_healthz, /_readyz), includes domain routers under version prefix (/v1). May gate routers by DEPLOYMENT_NAME/SERVER_TYPE. |
| `app/routing.py` | `CustomRequestRoute(APIRoute)`: wraps route handler for request/response logging, timing, centralized exception handling to ResponseData envelope. |
| `app/connection.py` | `ConnectionManager` (singleton via `__new__` or Singleton metaclass): creates AsyncEngine, scoped session factory, Redis client. `ConnectionHandler` (per-request): lazy .session/.redis properties, RLS/schema-switching helpers. `get_connection_handler()`: FastAPI dependency generator. |
| `app/dao.py` | `BaseDao`: generic async DAO with create/get_by_pk/update_by_pk/delete_by_pk/get_by_filter/get_paginated_response/bulk_insert/bulk_update. Soft-delete aware. All queries through _execute_query (auto-rollback on error). |
| `app/database.py` | `Base` declarative base (DeclarativeBase in SQLAlchemy 2.0, declarative_base() in 1.4). All ORM models inherit from Base. |
| `app/lifetime.py` | `@asynccontextmanager async def lifespan(app: FastAPI)`: startup (setup_logging, init ConnectionManager, Kafka producer, Temporal client, Redis), shutdown (close ConnectionManager, dispose engine, close Redis, shutdown telemetry). |
| `app/main.py` | uvicorn.run("app.application:get_app", factory=True, host=..., port=...). Invoked by entrypoint.py in server mode. |
| `config/settings.py` | `Settings(BaseSettings)`: typed env vars (DATABASE_URL, REDIS_URL, DEBUG, CORS_ORIGINS, KAFKA_*, TEMPORAL_*, etc.). Module-level singleton: `settings = Settings()`. All code imports settings from here. |
| `services/kafka/consumer/consumer.py` | async def main(): infinite loop consuming Kafka topics, processing messages, acknowledging. Called by entrypoint.py in consumer mode. |
| `services/temporal/run.py` | async def worker_main(): registers workflows/activities, runs Temporal worker. Called by entrypoint.py in temporal_worker mode. |

## Domain layouts

### Flat layout

Used for rapid iteration, monolithic services with many domains but no API versioning.

```
src/
├── product/
│   ├── __init__.py
│   ├── router.py         # product_router = APIRouter()
│   ├── service.py        # ProductService: business logic
│   ├── dao.py            # ProductDao(BaseDao): DB queries
│   ├── models.py         # ProductModel(Base): ORM model
│   ├── schemas.py        # ProductSchema, ProductListSchema: Pydantic request/response
│   ├── helper.py         # Domain-specific utilities
│   └── constant.py       # Enums, constants
├── category/
│   ├── router.py
│   ├── service.py
│   ├── dao.py
│   ├── models.py
│   ├── schemas.py
│   ├── helper.py
│   └── constant.py
├── order/
│   ├── router.py
│   ├── service.py
│   ├── dao.py
│   ├── models.py
│   └── schemas.py
└── ... (many domain modules)
```

**Router aggregation** (in src/main.py or app/router.py):

```python
from src.product.router import product_router
from src.category.router import category_router
from src.order.router import order_router

api_router = APIRouter()
api_router.include_router(product_router, prefix="/v1/products", tags=["Products"])
api_router.include_router(category_router, prefix="/v1/categories", tags=["Categories"])
api_router.include_router(order_router, prefix="/v1/orders", tags=["Orders"])
```

**Pros**: Simple, flat namespace, easy to find files, minimal directory nesting.

**Cons**: No API versioning support. Changing a schema breaks all clients.

### Versioned layout

Used for API evolution, side-by-side v1/v2 implementations, gradual migration.

```
app/
├── identity/
│   ├── __init__.py
│   └── v1/
│       ├── __init__.py
│       ├── router.py         # identity_v1_router = APIRouter(prefix="/identity")
│       ├── user/
│       │   ├── router.py     # user_router
│       │   ├── service.py
│       │   ├── dao.py
│       │   ├── models.py
│       │   └── schemas.py
│       ├── group/
│       │   ├── router.py
│       │   ├── service.py
│       │   └── ...
│       └── session/
│           ├── router.py
│           └── ...
├── access/
│   └── v1/
│       ├── router.py         # access_v1_router = APIRouter(prefix="/access")
│       ├── policy/
│       │   ├── router.py
│       │   ├── service.py
│       │   └── ...
│       └── delegation/
│           ├── router.py
│           └── ...
└── control/
    └── v1/
        ├── router.py         # control_v1_router = APIRouter(prefix="/control")
        ├── tenant/
        │   ├── router.py
        │   └── ...
        └── audit/
            ├── router.py
            └── ...
```

**Router aggregation** (in app/router.py):

```python
from app.identity.v1.router import identity_v1_router
from app.access.v1.router import access_v1_router
from app.control.v1.router import control_v1_router

api_router = APIRouter()
api_router.include_router(identity_v1_router, prefix="/v1")
api_router.include_router(access_v1_router, prefix="/v1")
api_router.include_router(control_v1_router, prefix="/v1")
```

Final routes: `/v1/identity/users`, `/v1/access/policies`, `/v1/control/tenants`.

**Pros**: API versioning built-in. Can add v2/ alongside v1/ without breaking clients. Gradual migration path.

**Cons**: More directory nesting. Slightly more boilerplate for router aggregation.

## Monorepo layout

Used for multi-service codebases sharing common packages.

```
myservice/
├── apps/                      # Deployable services
│   ├── api/                   # Main API service
│   │   ├── app/
│   │   │   ├── application.py
│   │   │   ├── router.py
│   │   │   └── lifetime.py
│   │   ├── config/
│   │   ├── domains/
│   │   └── entrypoint.py
│   ├── orchestrator/          # Workflow orchestration service
│   │   ├── app/
│   │   ├── config/
│   │   └── entrypoint.py
│   ├── node_workers/          # Background task workers
│   │   ├── app/
│   │   └── entrypoint.py
│   └── signal_forwarder/      # Event forwarder
│       ├── app/
│       └── entrypoint.py
├── packages/                  # Shared libraries
│   ├── common/                # Utilities (logging, metrics, auth)
│   ├── contracts/             # API contracts (jsonschemas, Pydantic models)
│   │   └── jsonschemas/
│   ├── db/                    # Shared database models, alembic
│   │   ├── models/
│   │   ├── alembic/
│   │   └── connection.py
│   └── sdk/                   # Internal SDK for service-to-service calls
│       └── client.py
├── services/                  # Infra packages (Kafka, Temporal)
│   ├── kafka/
│   └── temporal/
└── pyproject.toml             # Monorepo-wide dependencies
```

**Deployment**: Each app/ directory is a separate Docker image. Shared packages/ are installed as local dependencies.

**Pros**: Single source of truth for shared code. Consistent versioning across services. Easier refactoring.

**Cons**: More complex build/deploy pipeline. Must coordinate changes across services.

---

## Multi-deployment layout

Used for single codebase serving multiple deployment types (public/internal/platform/webhook) with different router sets.

```
myservice/
├── entrypoint.py
├── app/
│   ├── application.py         # Sets root_path=f"/service/{SERVER_TYPE}/product/feature"
│   ├── router.py              # Conditionally includes routers based on loaded_config.SERVER_TYPE
│   └── ...
├── config/
│   └── docker_config.py       # SERVER_TYPE env var
├── order/
│   └── routers.py             # Included in public, internal
├── config/
│   └── routers.py             # Included in internal, platform
├── integrations/
│   └── partner/
│       └── routers.py         # Included in webhook only
└── billing/
    └── routers.py             # Included in public, internal
```

**Router gating** (in app/router.py):

```python
if loaded_config.SERVER_TYPE == "public":
    api_router_prefix.include_router(order_router)
    api_router_prefix.include_router(billing_router)

elif loaded_config.SERVER_TYPE == "internal":
    api_router_prefix.include_router(order_router)
    api_router_prefix.include_router(billing_router)
    api_router_prefix.include_router(config_router)

elif loaded_config.SERVER_TYPE == "platform":
    api_router_prefix.include_router(config_router)

elif loaded_config.SERVER_TYPE == "webhook":
    api_router_prefix.include_router(partner_router)
```

**OpenAPI path rewriting** (in app/application.py):

```python
def custom_openapi(app: FastAPI):
    openapi_schema = get_openapi(...)
    url_prefix = f"/service/{loaded_config.SERVER_TYPE}/{product_path}"
    paths = {}
    for path, path_item in openapi_schema["paths"].items():
        paths[f"{url_prefix}{path}"] = path_item
    openapi_schema["paths"] = paths
    return openapi_schema
```

**Pros**: Single codebase for multiple deployment types. Reduces duplication. Easier to maintain shared logic.

**Cons**: More complex routing logic. Must carefully test all deployment types. Potential for accidental exposure of internal routes.

## Choosing a layout

| Layout | Use when |
|--------|----------|
| **Flat** | Rapid iteration, no API versioning needed, monolithic service, <50 domains |
| **Versioned** | API evolution required, gradual migration, side-by-side v1/v2 implementations |
| **Monorepo** | Multiple services sharing common code, coordinated releases, single source of truth |
| **Multi-deployment** | Single codebase for multiple deployment types (public/internal/platform), different router sets per deployment |

**Never mix flat and versioned layouts** in the same service. Pick one and stick with it.
